# Короткие ссылки на JSON заданий

Статус: локальная реализация; в production не развёрнута. По умолчанию
`MAX_SHORT_LINK_MODE=off`, сохраняется отправка длинных ссылок.
По обновлённому решению пользователя оба режима используют **48 часов**
(172800 секунд); это заменяет исходную договорённость о 24 часах.

## Архитектура

`index.task_handler` читает и проверяет исходный JSON. В режиме `on` он создаёт
или читает одну закрытую запись в существующем бакете
`1bf11148-3595-4a07-a089-d460153b7c7a`, под префиксом `_max-short-links/v1/`.
Публичная отдельная Cloud Function с entrypoint `short_links.handler` принимает
только непрозрачный ID и возвращает HTTP 302 на сохранённый URL. Она не вызывает
MAX и не создаёт ссылки. Формат адреса: `https://<approved-endpoint>?id=<32 chars>`;
для прямого URL Cloud Functions используется `?tag=production-stable&id=...`.

Выбрано **хранение уже подписанного URL**, а не новое подписание при переходе.
Это фиксирует срок в самой подписи S3: 172800 секунд от первой подготовки
ссылки. Сервис переходов не нуждается в правах на чтение исходных заданий или
в ключе HMAC отправителя. Повторное создание и параллельные запросы возвращают
одну запись. Срок берётся из `X-Amz-Date` и `X-Amz-Expires`, проверяется при
каждом переходе и не продлевается. Подписывается GET с
`ResponseContentDisposition=attachment` и `ResponseCacheControl=no-store`.

ID — первые 192 бита HMAC-SHA256 от фиксированного пространства имён, бакета
и ключа объекта, в base64url (32 символа). Ключ HMAC — 32 случайных байта;
публичные имена заданий не позволяют вычислить ID. HMAC также даёт стабильный ID
после перезапуска процесса. Смена содержимого по тому же ключу не создаёт новый
срок: контроль SHA-256 останавливает повторную отправку и требует сверки.
Хеш содержимого не используется для вычисления ID.

Запись создаётся через `PutObject(IfNoneMatch="*")`. При гонке или потерянном
подтверждении записи читается победившая запись. Если её существование не
подтверждено, MAX не вызывается. Это опирается на документированные
[условные записи Yandex Object Storage](https://yandex.cloud/en/docs/storage/concepts/object#conditional-writes).
Записи не удаляются после истечения срока: они сохраняют идемпотентность и
ответ 410. Не добавлять TTL-удаление или ротацию HMAC без отдельной миграции.

Сервис проверяет точный HTTPS-хост `storage.yandexcloud.net`, бакет, путь
`equipment-tasks/T-[A-Za-z0-9_-]+.json`, допустимые параметры SigV4 и срок.
URL от клиента, произвольные bucket/key и параметры перенаправления запрещены.
Параметры versionId поддержаны, если исходный GET вернул реальную версию.

## HTTP и ошибки

| Условие | Ответ |
|---|---|
| Действующий ID, GET | 302, исходный подписанный URL в Location |
| Действующий ID, HEAD | 200 без Location и тела (подпись GET не подходит для HEAD) |
| Неизвестный или некорректный ID | 404 |
| Истёкшая запись, включая точную границу срока | 410 |
| Дополнительные/повторные параметры | 400 |
| POST/PUT/DELETE и прочие методы | 405 |
| S3 недоступен, AccessDenied, повреждённая запись, ошибка часов | 503, Retry-After: 30 |

Ответы содержат `Cache-Control: no-store`, `Referrer-Policy: no-referrer` и
`X-Robots-Tag: noindex`. Приложение не пишет ID, URL, входные события,
Location, тела записей или детали исключений в лог. Доступ к реестру закрытый:
его содержимое даёт возможность скачивания до истечения срока.

В режиме `on` ошибка реестра не переключает автоматически на новую длинную
ссылку — иначе можно незаметно продлить доступ. Возврат к старому поведению
выполняется явно режимом `off` либо откатом версии. Оба режима используют
согласованный компактный формат MAX: `format=html`, заголовок, экранированный
task_id, `<a href="escaped URL">📄 Скачать JSON</a>`, query
`disable_link_preview=true`; предупреждение о загрузке файлов убрано.
Поведение доставки MAX сохранено:
один POST, HTTP/business error или timeout — ошибка без внутреннего повтора.
Идемпотентность ссылок **не является exactly-once доставкой MAX**. Триггер может
повторно доставить событие; журнал восстановления и ручная сверка остаются нужны.

## Настройки и минимальные права

| Настройка | Где нужна |
|---|---|
| `MAX_SHORT_LINK_MODE=off/on` | Только отправитель заданий; по умолчанию off |
| `MAX_SHORT_LINK_BASE_URL` | Отправитель; согласованный HTTPS-адрес; без query либо с `tag=production-stable` |
| `MAX_SHORT_LINK_HMAC_KEY` | Отправитель; 64 hex-символа из криптографического генератора; хранить как секрет |
| S3 credentials | Отправитель и resolver, каждый со своим необходимым доступом |

Клиент коротких ссылок фиксирует endpoint, ru-central1, SigV4 и path addressing;
`S3_ENDPOINT` не может направить его в другой сервис. Существующие зависимости
не меняются. Для записи реестра отправителю нужны GetObject и условный PutObject
только на `_max-short-links/v1/*`, помимо уже существующего чтения заданий.
Resolver нужны только чтение реестра и возможность получить достоверный
NoSuchKey для отсутствующей записи. При необходимости ListBucket для различения
404/403 его объём нужно отдельно согласовать; AccessDenied код не маскирует
под неизвестную ссылку. Resolver не получает MAX credentials и HMAC-ключ.

Не делать бакет публичным. Публичным становится только отдельный resolver
(либо согласованный маршрут API Gateway). Для прямой Cloud Function использовать
стабильный тег в URL: вызов без тега обращается к `$latest`.
[Формат HTTPS-вызова и ответа](https://yandex.cloud/en/docs/functions/concepts/function-invoke),
[вызов версии по тегу](https://yandex.cloud/en/docs/functions/operations/function/function-invoke).

Важное ограничение существующего хранилища: без versioning подписанная ссылка
привязана к **ключу**, а не к неизменяемым байтам. Реализация ничего не меняет
в исходном JSON; при неизменном объекте скачивается тот же файл. Если другой
процесс перезапишет его после выдачи ссылки, S3 вернёт новое содержимое.
Для строгой гарантии исторических байтов потребуется отдельно согласовать
versioning или неизменяемую копию. В этой работе ни то ни другое не включено.
Учётные данные подписавшего аккаунта должны оставаться действующими на весь
срок ссылки; отзыв ключа может прекратить доступ раньше.

## Проверки

```sh
python -m unittest discover -s max-messenger-notifier -p 'test_*.py' -v
python -m unittest discover -s scripts -p test_max_release.py -v
```

Тесты не используют облако/MAX. Покрыты гонка 8 создателей, потерянный ответ
PutObject, недоступность/AccessDenied, отсутствие записи, точная граница 48 часов,
непродление срока, смена содержимого, подмена URL, отсутствие секретов в логах,
HTTP GET/HEAD, контроль входных параметров, штатный fallback, ошибки доставки
MAX и состав ZIP. HTTP-тест поднимает только сервер 127.0.0.1, следует редиректу
на локальный источник и сравнивает сырые байты, включая пробелы и CRLF.

Для отдельной проверки реального S3 подготовлен
`scripts/check_short_link_download.py --key equipment-tasks/T-<approved-id>.json`.
Он использует существующие credentials окружения, читает исходник, сохраняет
реестр только в RAM, открывает локальный HTTP resolver, скачивает настоящий
подписанный URL и сравнивает байты, SHA-256 и Content-Disposition. Секреты,
URL и содержимое JSON не выводятся. Записей S3 и сообщений MAX нет.
**Эта проверка ещё не выполнена:** автоматическая проверка разрешений отклонила
попытку получить S3 credentials из environment действующей Cloud Function.
Необходим отдельный разрешённый источник credentials либо явное согласование
их чтения из этой версии; отказ не обходился.

## Согласуемый выпуск

1. Утвердить адрес, отдельную функцию resolver и оплату её вызовов/хранения
   небольшого реестра в существующем S3. Рекомендуемый первый вариант —
   служебный HTTPS Cloud Functions без покупки домена и без изменения двух
   существующих шлюзов. Утвердить точные IAM/policy changes и источник credentials
   для проверки. До этого облако не менять.
2. Принять проверенный код; собрать воспроизводимый ZIP через
   `python scripts/max_release.py build` из чистого коммита. Manifest включает
   `short_links.py`. Обычный deploy этого скрипта относится **к отчётам**;
   не использовать его для развёртывания resolver/заданий.
3. Создать отдельный resolver с `short_links.handler`, закрытым доступом к реестру,
   без секретов MAX и HMAC. Публичный вызов включить только для него или
   согласованного API Gateway. Ограничить нагрузку/расходы. Отключить access logs
   с query string/Location/телами на всём новом HTTP-маршруте; не включать
   botocore DEBUG, request/response tracing. Убедиться, что платформенные логи
   не сохраняют capability ID или подписанный URL. Зафиксировать production-stable.
4. Проверить реальные условные записи/гонку и NoSuchKey на разрешённой
   диагностической записи **только** под `_max-short-links/v1/`, без новых
   `equipment-tasks/T-*` и без изменения `Задания/`. Проверить HTTP 404, 410,
   503, no-store; источник для скачивания — отдельно согласованный существующий
   JSON. Сравнить SHA-256 при реальном переходе через облачный HTTPS endpoint.
   Проверить оставшийся TTL в сохранённой подписи и контрольные истёкшие записи.
   Не использовать рабочий MAX-чат для тестов без разрешения.
5. Сохранить конфигурацию/маршрут отправителя в памяти, фильтровать environment
   из всех выводов. Убедиться, что stable всё ещё `d4eq7772aa4o2uelvcm8` (либо
   сверить новую рабочую версию). Создать кандидат **отдельно** в функции
   `d4epetugkbfvm0jnag03`, entrypoint `index.task_handler`, 256 MiB, сохранив
   её собственные настройки и получателя. Добавить только согласованные
   параметры коротких ссылок. Новую версию проверить пустым `{"messages":[]}`;
   это smoke runtime, не проверка доставки. Создание версии переносит `$latest`,
   поэтому производственный триггер должен оставаться на `production-stable`.
6. После полной проверки и явного согласования производственного переключения
   сохранить rollback-тег старой версии и перенести только `production-stable`.
   Не менять фильтры/состояние триггера, не инициировать его вручную. Наблюдать
   только естественно появляющееся новое задание, сверить ровно одно ожидаемое
   уведомление и скачивание. Уже восстановленные сообщения не отправлять.

## Откат

Вернуть `production-stable` отправителя на сохранённую предыдущую версию
с длинными ссылками и согласованным компактным HTML-форматом. На момент
первой инвентаризации была активна `d4eq7772aa4o2uelvcm8`; параллельно
выпущено HTML-форматирование (`d4e72de73k8d91dv4msf`) и готовится выпуск
48 часов из PR #18, поэтому перед действием
обязательно заново проверить baseline и сохранить его точный ID.
Это возвращает длинные ссылки для будущих событий. Не возвращаться на старую
версию с неисправной загрузкой файлов. Не вызывать задания повторно, не трогать
очереди и Celery. При неоднозначном результате MAX сначала сверить журнал
доставки и сообщение, даже если причиной отката был resolver.

Сохранить resolver, его stable-версию, credentials и реестр как минимум до
окончания всех выданных ссылок; для стабильного 410 и идемпотентности сохранять
реестр и далее. Откат отправителя не отзывает уже отправленные короткие ссылки.
При аварии resolver возвращать его ранее проверенную версию с тем же форматом
реестра. Не удалять записи и не менять HMAC в рамках отката.

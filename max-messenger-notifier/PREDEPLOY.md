# Предрелизная проверка MAX-уведомителя

Дата проверки: 31.07.2026

## Проверено

- отчёт v1 прочитан обработчиком непосредственно из тестового Object Storage;
- отправка в MAX в smoke-тесте заменена перехватчиком;
- для исторического v1 без `palletNumbers` сохраняется одна сводка без
  паллетного ярлыка;
- для v1 нового задания с одним назначенным `palletNumbers` весь отчёт
  преобразуется в один паллет и отправляется только ярлык с SSCC без
  дополнительной сводки;
- для v1 отклоняются несколько назначенных паллетных SSCC;
- эталонные отчёты xTrek v2 для UNIT и SET успешно разобраны;
- для v2 проверяются ID файла, отчёта и задания;
- для v2 проверяются закрытие паллетов и коробов, контрольные цифры SSCC и
  принадлежность паллетов заданию;
- на ярлыке выводятся SSCC, оператор, количество коробов и количество штук
  конкретного паллета;
- ошибка одного паллетного ярлыка не мешает сформировать следующие;
- GS1-128 независимо прочитан ZBar и ZXing-C++;
- зависимости установлены в чистый каталог из `requirements.txt`;
- успешно выполнены 27 автоматических тестов;
- на фактической паре нового производственного задания и v1-отчёта
  `T-GB-8549-77-001-02.2029-C-02-28-e19ec6bc-84d2-4aaf-a4ab-736dc9ca84ff`
  при перехваченной отправке подтверждён один PNG-ярлык:
  SSCC `046070517921693749`, 15 коробов, 60 штук, оператор
  `87455043efffbb66`.

## Сознательно не проверялось

- запуск версии в Yandex Cloud Functions;
- промышленный триггер Object Storage;
- реальная загрузка вложений и доставка сообщений в MAX;
- фактическое время выполнения функции при большом числе паллетов;
- повторная доставка одного и того же события Object Storage.

Эти пункты нельзя считать подтверждёнными локальными тестами.

## Перед включением промышленного триггера

1. Проверить diff и принять PR.
2. Создать новую версию функции без переключения промышленного трафика.
3. Сверить переменные `MAX_BOT_TOKEN`, `MAX_CHAT_ID`, `S3_ENDPOINT`,
   `EQUIPMENT_TASKS_BUCKET` и `EQUIPMENT_TASKS_PREFIX`.
4. Убедиться, что роль функции читает и `equipment-reports/`, и
   `equipment-tasks/`.
5. Проверить установленный timeout с учётом последовательной отправки одного
   сообщения на каждый паллет.
6. Выполнить контролируемый ручной вызов новой версии сначала с v1, затем с
   v2 на два паллета.
7. Для v2 проверить сканером каждый полученный ярлык и сверить SSCC,
   оператора, число коробов и число штук.
8. Только после этого переключить промышленный триггер на новую версию.
9. Сохранить возможность немедленно вернуть предыдущую версию функции.

## Наблюдение после переключения

- ошибки чтения `equipment-tasks/`;
- несовпадение ID файла, отчёта и задания;
- `attachment.not.ready` и окончательные ошибки MAX;
- длительность обработки отчётов с несколькими паллетами;
- повторные уведомления по одному ID отчёта;
- отсутствие одного из ярлыков при частичной ошибке доставки.

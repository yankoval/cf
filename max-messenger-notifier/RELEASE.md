# Публикация MAX notifier через GitHub

Workflow: [MAX notifier](https://github.com/yankoval/cf/actions/workflows/max-notifier.yml).
Публикация запускается вручную через **Run workflow** из основной ветки.
PR запускает только тесты и сборку, без доступа к облаку.

## Что публикуется

Архив содержит только `index.py`, `short_links.py`, `requirements.txt`, `DejaVuSans.ttf`, `russian-root.pem` и
сгенерированный `build-info.json`. SHA полного коммита, хеши каждого файла и
сводный хеш исходников записываются в manifest. SHA-256 готового ZIP записывается
отдельно. Workflow проверяет соответствие скачанного артефакта своему коммиту и
передаёт именно эти байты в API Cloud Functions, без повторной упаковки.

Этот workflow по-прежнему публикует **только отчёты** (`index.handler`,
`d4ep5laqq7maeesp0lcd`). Отправитель заданий и отдельный HTTPS-обработчик
коротких ссылок требуют отдельного согласованного выпуска:
[SHORT-LINKS.md](SHORT-LINKS.md). Само включение нового модуля в архив
не включает короткие ссылки.

В описание облачной версии попадают полный Git SHA, SHA-256 архива и исходников,
ссылка на запуск Actions. ZIP, `manifest.json`, `SHA256SUMS` и `deployment.json`
сохраняются как артефакты Actions на 90 дней и как assets отдельного GitHub
Release без автоматического срока удаления. `build-info.json` не содержит
времени сборки или номера запуска: повторная упаковка одинакового коммита с
одинаковыми файлами даёт одинаковые байты в одной версии инструмента сборки.

`requirements.in` задаёт четыре прямые зависимости; `requirements.txt` фиксирует
все 13 прямых и транзитивных зависимостей с хешами PyPI. Включены
`--require-hashes` и `--only-binary=:all:`. Первые версии взяты из проверенного
окружения Python 3.14 от 22.09.2026. Это **новый контролируемый набор библиотек**;
он не объявляется побайтовой копией библиотек исторического облачного выпуска.
Управляемый runtime `python314` и его системные библиотеки обновляются облаком
независимо от репозитория.

## Однократная настройка доступа и маршрута

1. Создать сервисный аккаунт `cf-github-deployer` в каталоге
   `b1g66di24cjhduu1tdoc`.
2. Для первого процесса выпуска выдать аккаунту `functions.editor` на MAX
   `d4ep5laqq7maeesp0lcd`. Аккаунт общий для репозитория: при подключении других
   компонентов назначать этому же аккаунту роль на их явно проверенные
   Function ID. Перечень назначений должен соответствовать связке
   «каталог исходников в `yankoval/cf` → облачные функции». Роль позволяет читать
   конфигурацию, создавать версии, вызывать и удалять подключённые функции,
   менять их теги. Права на общий облачный каталог автоматически не выдаются.
3. Связать аккаунт с существующей GitHub OIDC-федерацией
   `aje2njl999g9l6u3s5i6`, subject
   `repo:yankoval/cf:environment:cf-deploy`.
   Долгоживущие облачные ключи в GitHub не требуются.
4. Создать GitHub Environment `cf-deploy`. Разрешить deployments только
   из текущей основной ветки
   `feature/task-agg-worker-function-15501132681682912444` и добавить environment
   variable `YC_CF_DEPLOY_SA_ID` с ID нового аккаунта. При переименовании основной
   ветки обновить это правило. Сам workflow определяет основную ветку из события.
5. Убедиться, что `$latest` всё ещё указывает на проверенную версию
   `d4edek01oau4qdoe04mg`. Назначить ей теги `production-stable` и
   `baseline-20260922`. У триггера `a1sj4qbd8f0j3t3p1mdo`
   изменить только `function_tag` с `$latest` на `production-stable`.
   Сверить, что ID вызываемой версии, фильтры бакета и статус не изменились.
   Сделать это **до** создания первой новой версии: `$latest` переносится
   автоматически, даже если публикация впоследствии завершится неудачей.

При использовании `yc serverless trigger update object-storage` указывать
полный маршрут, включая существующие фильтры. Проверено при активации:
передача только нового тега отклоняется, а передача параметров действия без
`--new-prefix` и `--new-suffix` сбрасывает фильтры. Для данного триггера:

```sh
yc serverless trigger update object-storage \
  --id a1sj4qbd8f0j3t3p1mdo \
  --new-bucket-id 20ab2a0c-2726-4ba1-9c7c-7deae82941ff \
  --new-prefix equipment-reports/T- --new-suffix json \
  --new-events create-object \
  --new-invoke-function-id d4ep5laqq7maeesp0lcd \
  --new-invoke-function-tag production-stable \
  --new-invoke-function-service-account-id ajej4768auhje9fqp5us
```

Перед командой сохранить актуальный `rule` триггера, после неё сравнить весь
`rule`: единственным отличием должен быть `function_tag`. Команда выше
применима только при сохранении перечисленных ID и фильтров. Обычные выпуски
через workflow сам триггер больше не обновляют, а переносят тег версии.

Существующие полномочия владельца облака сохраняются для аварийного
восстановления. Настройка не отменяет у него техническую возможность ручной
публикации. Штатные выпуски выполняются только этим workflow; отсутствие
соответствующего успешного запуска и сохранённого пакета означает, что версия
не имеет подтверждённого происхождения из GitHub.

## Общий аккаунт репозитория

`cf-github-deployer` обслуживает процессы публикации компонентов `yankoval/cf`.
Для следующих функций используются та же OIDC-связь, Environment `cf-deploy`
и переменная `YC_CF_DEPLOY_SA_ID`; новый сервисный аккаунт для каждой функции
не требуется. Назначения IAM расширяются по мере подключения подтверждённых
функций. Неизвестное происхождение legacy-функции не является основанием
автоматически включать её в перечень. В этой поставке реализован выпуск MAX.

Yandex IAM ограничивает доступ облачными ресурсами, а не каталогами GitHub.
Поэтому каждый workflow, получивший токен общего аккаунта, технически имеет
права на все подключённые функции. Отдельные workflows и concurrency-группы
помогают организовать выпуски, но не создают границы облачных полномочий.
В частности, группа `max-production` сериализует только публикации MAX.
Если в дальнейшем потребуется изоляция тестовых и промышленных публикаций,
нужны два аккаунта с разными правами и OIDC-связями, а не только два имени
GitHub Environment. Текущий общий доступ разрешён workflow из основной ветки.

Роль на каждой существующей функции позволяет выпускать её версии.
Создание совершенно новой функции потребует отдельного первоначального
создания и назначения доступа. Роль на весь cloud folder имеет смысл
рассматривать только для выделенного каталога ресурсов `cf`: существующий
общий каталог содержит также функции других проектов.

Основание: [область назначения ролей Cloud Functions](https://yandex.cloud/en/docs/functions/security/),
[GitHub OIDC и федеративные учётные данные](https://yandex.cloud/en/docs/iam/operations/wlif/setup-wlif).

## Выпуск

В **Run workflow** указать `expected_current_version`: ID версии с тегом
`production-stable`. Поле `rollback_version` оставить пустым.

Workflow выполняет тесты, собирает ZIP, получает краткоживущий IAM-токен через
GitHub OIDC и проверяет текущий ID. Конфигурация действующей версии, включая
environment и ссылки на Lockbox, переносится в памяти процесса. Значения
секретов не сохраняются в артефакты, Git или отчёт.

Новая версия сначала получает уникальный тег `gh-<run>-<attempt>`. После её
сборки workflow сверяет конфигурацию и вызывает обработчик с `{"messages": []}`.
Проверка загружает runtime, зависимости и настройки; отчёты не читаются,
сообщения MAX не отправляются. Она не проверяет фактическую доставку в MAX.
При неуспехе рабочий тег остаётся на прежней версии.

Непосредственно перед переключением повторно проверяется исходный ID;
параллельные публикации workflow сериализованы. Старая версия получает тег
`rollback-<run>-<attempt>`, затем `production-stable` переносится на проверенную
новую версию. Ручные изменения тегов во время публикации запрещены рабочим
порядком: облачный SetTag не предоставляет атомарного compare-and-swap.

## Откат

Повторно запустить тот же workflow из основной ветки, указав текущий ID в
`expected_current_version`, а сохранённый старый ID — в `rollback_version`.
Новая версия при откате не создаётся. Workflow проверит принадлежность старой
версии функции, выполнит пустой вызов и перенесёт `production-stable`.
`deployment.json` в выпуске отката указывает фактически восстановленную версию;
приложенный ZIP отражает ревизию workflow, а не исторический пакет отката.

## Обновление зависимостей

Изменить выбранные версии в `requirements.in`, затем в чистом Python 3.14
с установленным `pip-tools` пересоздать полный lock:

```sh
pip-compile --generate-hashes --strip-extras \
  --pip-args='--only-binary=:all:' \
  --output-file=max-messenger-notifier/requirements.txt \
  max-messenger-notifier/requirements.in
```

Сохранить строки `--require-hashes` и `--only-binary=:all:` в итоговом lock.
Проверить diff и оба набора тестов в PR перед публикацией.
